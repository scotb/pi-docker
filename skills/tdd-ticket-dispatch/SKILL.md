# TDD Ticket Dispatch

## When to Use
Dispatching a worker for any ticket marked TDD. Use this template for the subagent task text.

## Procedure
1. From the ticket, extract the Behavior contract bullets → named driver tests (snake_case, behavior-first). Type-level items (DateOnly, IReadOnlyList, immutability) go to an "API/type guarantees" note — compiler-enforced, no tests, no reflection.
2. Pre-agree the slice plan: driver tests in slice order, characterization labels, and shared-change groups — including PREDICTABLE shared greens (a positive bullet whose behavior will already be implemented by an earlier slice, e.g. a coexistence test whose uniqueness logic lands in an earlier red slice). Fixed before dispatch.
3. Dispatch one worker run per ticket with the orchestrate skill's 2-HOUR dispatch timeout (timeoutMs: 7200000 — always explicit, never the 30-minute default) + assess/resume policy — a TDD ticket with many slices or a live-DB integration suite may legitimately hit the wall; resuming from the ledger's last green is the expected recovery path, not a failure (2026-10: both timed-out TDD/UI tickets resumed successfully from near-complete trees). The task text IS the procedure authority (forked children get NO available_skills block). It carries only ticket-specific facts: (a) first line: follow the red→green vertical-slice loop exactly — one test → run and observe red → minimal implementation → run and observe green → next; (b) exact in-scope file list, "touch only these files"; (c) the pre-agreed slice plan (names, order, characterization labels, shared groups); (d) every red/green run is a single real BARE `dotnet test ... --filter ...` shell command — NO PIPES (the ledger parses the shell result text; pipes that drop the Passed!/Failed! summary line lose attribution); (e) STAGED REDS BANNED; (f) prohibitions: no temp files/cleanup/deletions, no git except commits on the ticket branch (no branch ops), no push, do NOT run or analyze the tdd-ledger or verify.mjs (orchestrator's gate); (g) close procedure IMMEDIATELY after the final full-suite run, before any stall/compaction window: append per-slice evidence table to ticket `## Comments` → Status: resolved; the worker makes no final commit — bookkeeping is committed and the ticket branch squash-merged by the orchestrator at close; (h) brief report (files, per-slice red/green evidence, commit SHA, final test line); (i) BOUNDARY SWEEP: if a slice writes a date/week/boundary/rounding/formatting helper, it must be tested across the boundary values (all 7 days of the week, empty input, min/max, zero/one) — not just the happy-path anchor; (j) COMMENT ACCURACY: code comments must describe what the code DOES; hand-verify any non-trivial formula before writing a comment about it. Do NOT restate red/green loop mechanics beyond line (a).
4. While the worker runs, the PARENT STAYS IDLE (shared local inference backend; parent turns slow the child ~5x). Dispatch → end the turn (at most one short status line) and resume on the native completion notification — no polling, no blocking waits. Stall monitoring within a run: if the ledger shows no new entries for >25 min on a run that should pace ~70s/slice, treat as stalled and resume from the ledger's last green.
5. At close (parent): full `dotnet test`; then the ledger verifier, ALWAYS session-scoped: `node ~/.pi/tdd-ledger/verify.mjs ~/.pi/tdd-ledger/<repo>.jsonl --session <child-sid-prefix> --drivers "<driver tests>" [--shared "<pre-declared shared tests>"] [--characterization "<labeled ones>"]`. Without --session, cross-session bleed produces false R1 fallbacks / R2 / R6. Hard FAIL (R1/R2) → reject the slice, re-dispatch from that slice. Warnings (R3/R4/R6) → review before accepting.
6. Append the verifier verdict (command + per-driver results + shared-green notes/adjudications) to the ticket `## Comments`; mark resolved; commit to the ticket branch.
7. Two-axis review at close (reviewer agent, BOTH axes in one run — no subagents, local LLM serializes): Standards (AGENTS.md/CONTEXT.md/ticket style) + Spec (ticket contract + evidence table). Adjudicate findings: the ticket contract is the authority; spec-invented requirements are rejected; design divergences are fixed by a worker TDD fix run (genuine runtime red, e.g. asserting current behavior via the wrong signature) with pre-declared shared call-site groups. Append adjudication to the ticket, commit to the ticket branch.
## Pitfalls
- Compile error is not a red. A compilable stub is OK only so the test compiles and then fails at runtime.
- Staged reds (write-everything-then-revert-to-stub, or comment-out) pass prose rules; only the ledger's raw+comment-stripped hash timeline catches them.
- Workers spontaneously "clean up" temp artifacts — forbid deletions explicitly in the task.
- Piped `dotnet test` runs can lose ledger test events (grep patterns without the Passed! line, or `head` SIGPIPE) → close-time R1 pairing breaks. Worse: the observed worker behavior on a lost event was 90+ min of self-diagnostic ledger forensics before timeout (observed re-run). Prohibit pipes in the dispatch AND add "do NOT run or analyze the tdd-ledger/verify.mjs" — the prohibition alone is a band-aid; no-pipes fixes the trigger.
- Long local-LLM worker sessions can hit mid-session context compaction (observed re-run at 03:34:46: the worker lost its position, re-derived state, and nearly duplicated work). Mitigate: keep tickets ≤ ~12 driver slices, and make the close procedure (bookkeeping) the FIRST action after the final full-suite run so a stall/compaction can't land between implementation and bookkeeping.
- Local LLM stalls: 29 min of zero session entries observed between slices. Stall rule: >25 min of ledger silence on a ~70s/slice run → resume from the ledger's last green.
- Boundary-logic blind spot (2026-10): a worker wrote a week-start formula, wrote a comment claiming the OPPOSITE of what the code does, and tested only a Monday anchor — the Sunday case returned the next Monday and shipped to the gate. The fix run (directed) added a 7-day theory test with genuine red/green and was clean. Hence the standing boundary-sweep (i) and comment-accuracy (j) lines in the dispatch.
- Verifier without --session bleeds cross-session state (false R1 fallback, false R2 staged-red, false R6 file-list noise). --shared exempts pre-declared shared-change greens from R1 (no red required).
- Unplanned shared greens: workers self-classify them in the report (verified 3/3 in the re-runs); the orchestrator declares them via --shared at close and records the plan defect in the ticket Comments. Worker "pre-agreed" phrasing for un-declared groups is a mild overclaim — adjudicate, don't rely on the label.
- Review adjudication principle: a finding requiring behavior not in the ticket contract, which the control implementation also lacks, is rejected as spec-invented. Divergence from control in design (without ticket mandate) can be accepted-as-P1 and fixed via a worker TDD fix run.
- Reflection in a unit test = architectural smell (user hard rule): redesign, don't test; type guarantees belong in the API/type-guarantees note.
- Driver test names passed to the verifier are the bare snake_case names (verifier suffix-matches FQNs). Build-failed ledger events are NOT reds (the verifier excludes them).
## Verification
- Full `dotnet test` green with 0 warnings (TreatWarningsAsErrors).
- Verifier verdict (session-scoped): 0 hard failures; warnings reviewed.
- Ticket `## Comments` per-slice evidence matches the captured ledger runs; verdict + shared-green notes + review adjudication appended.
- Boundary helpers carry boundary-sweep tests (all boundary values), not just happy-path anchors.
- All work (code, verdict, adjudication) committed on the ticket branch; the base branch gains exactly one squash commit per ticket (or fix) at close; no push.
